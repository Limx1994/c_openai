# 代码审查团队执行流程

## 目标与准入条件

主控负责范围、派发、进度与聚合裁决，业务分析由四个专业角色完成。只报告具备明确代码位置、现实触发路径和可验证证据的问题。排除理论猜测、极端边界、泛化健壮性建议、通用网络安全讨论和风格偏好。

| 角色 | 重点 | 必需证据 |
| --- | --- | --- |
| Bug 专员 | 逻辑、类型、状态、异常分支、崩溃与死锁 | 可复现输入及确定的调用链 |
| 性能专员 | 高频瓶颈、泄漏、不合理 I/O、资源释放 | 实际频率、规模和测量结果；不能仅凭复杂度推断 |
| 功能完成度专员 | TODO/FIXME、半成品逻辑、接口未闭环 | 项目需求、文档或调用方与实现的具体差异 |
| 死代码专员 | 不可达分支、废弃符号、冗余文件配置 | 全项目零引用分析，排除公共 API、回调、宏和构建入口 |

## 工具与批次安排

- 执行前分析已注册 MCP、skills 和内置工具；每轮请求先调用 sequential_thinking。
- 使用 PowerShell、rg 和项目现有验证脚本；修改问题前读取日志。
- 使用原生 collaboration 工具派发，不通过 ESM 脚本启动；不显式设置 model，继承默认配置。
- 当前总并发上限为 4，含主控；最多同时运行 3 位专员，空出槽位后派发第四位。四个专业角色不能被误写为同时启动四个子 Agent。
- 先审公共接口、配置和构建入口，再分批审客户端、JSON、curl、lwIP、脚本、测试、示例及维护文档。按文件体量拆批，保留接口和直接调用链上下文。
- 第三方库独立登记范围，固定版本后按模块分批；不得把检索命中或自动扫描等同人工深审。
- 分别记录自动扫描、全文阅读、人工深入复核的覆盖状态。工具不可用、用量限制和用户要求跳过的 Daybreak 任务均记录原因，不绕过限制。

## Task List

### 阶段一：准备与独立审查

- [ ] 列出代码、脚本和 MD 清单，区分维护文件、第三方、生成物和历史证据。
- [ ] 读取项目规范、相关跨项目记忆、日志及现有测试，定义成功标准。
- [ ] 为四个角色派发模块清单、接口上下文、证据门槛及只读权限。
- [ ] 各专员独立提交候选问题，记录路径、行号、符号、输入和验证结果。

### 阶段二：交叉质询与自我反思

- [ ] 涉及多个领域的候选必须交给相关专员复核：Bug 修复检查性能与功能影响，删除候选检查公开接口及功能依赖。
- [ ] 质询者尝试反驳触发条件、调用链和影响，保留验证命令与结果。
- [ ] 原专员重新复现并修正结论；无法排除反例或证据不足的候选不进入确认问题。
- [ ] 明确记录确认、撤回、证据不足或待复核，不把未复核写成共识。

### 阶段三：主控裁决与报告

- [ ] 主控去重并检查三项准入证据，保留跨专员意见，按实际影响排序。
- [ ] 输出确认问题及真实覆盖范围；待验证项与跳过项单独说明，不计入确认问题。
- [ ] 不给未经测量的代码质量评分，不设定固定时间内完成全库审查的保证。
- [ ] 审查阶段不修改文件；修复在用户授权后按最小范围进行并重新验证。

## 确认问题格式

- **[严重级别] 简短标题**
  - **领域**：Bug / 性能 / 功能完整度 / 死代码
  - **位置**：具体文件绝对路径:行号
  - **函数/符号**：相关入口及符号
  - **触发条件**：现实输入、配置与操作步骤
  - **实际影响**：可观察行为；性能问题给出实际测量
  - **证据（代码调用链/引用分析）**：可核对的源码与引用路径
  - **验证结果**：命令、输入、预期与实际结果
  - **交叉审查意见（其他专员的质询与复核结论）**：质询内容及证据
  - **建议修复**：最小变更和影响模块
